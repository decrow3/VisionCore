# BackImage Trajectory-Table Observer Implementation Pre-Mortem

Last curated: 2026-06-16.

This note anticipates implementation failures before writing the first runner.
It is based on the current BackImage aggregate runner, the Vernier
trajectory-table observer, and the new BackImage observer prescription.

## Highest-Risk Design Points

### 1. Known-Eye Needs A Separate True-Trajectory Candidate Table

In Vernier, the known-eye reference was easy because both labels shared a small
candidate table indexed by the true trace. In BackImage image-identity scoring,
known-eye means:

```text
known_score[i] = log p(y_obs | I_i, tau_true)
```

for every candidate image `I_i`.

If `trajectory_prior_mode = leave_one_out`, `tau_true` is intentionally absent
from the joint prior catalog. Therefore known-eye cannot be implemented by
indexing `lambda_counts[:, true_trajectory_index]` unless that index refers to
a separate known-eye table.

Recommended cache schema:

```text
prior_lambda_counts: [n_candidates, n_prior_trajectories, n_timebins, n_units]
known_lambda_counts: [n_candidates, n_timebins, n_units]
zero_lambda_counts:  [n_candidates, n_timebins, n_units]
y_obs_counts:        [n_timebins, n_units]
```

Then:

```text
joint_score = logsumexp/logmeanexp over prior_lambda_counts
known_score = score known_lambda_counts
zero_score  = score zero_lambda_counts
```

This avoids accidentally making known-eye unavailable or leaky in LOO mode.

### 2. Do Not Accumulate The Whole Raw Response Bank In Memory

The aggregate runner keeps `raw_responses` in memory because it immediately
compresses them into response summaries. The trajectory observer needs raw-ish
tables, so a giant in-memory bank can explode.

Approximate per-trial cache size:

```text
n_candidates * n_trajectories * n_timebins * n_units * 4 bytes
```

For `16 candidates x 16 trajectories x 40 time bins x 756 units`, this is about
`31 MB` for the prior table alone, before known/zero tables. Many observed
trials would become too large quickly.

Implementation rule:

- build one trial or one candidate-set table at a time;
- write a chunked `.npz` immediately;
- append a manifest row;
- release arrays before moving to the next trial.

For Stage 0/1, `np.savez_compressed` is acceptable. For larger runs, prefer
uncompressed `.npz` or a chunked array backend if compression becomes the
runtime bottleneck.

### 3. Raw Rates Are Not Counts

`CanonicalTwinScorer.responses(patch, traces)` returns time-by-unit rates. The
Poisson expected-count score needs counts:

```text
lambda_counts = rates * bin_seconds
y_obs_counts  = observed_rates * bin_seconds
```

The runner must record:

```text
bin_seconds
rate_to_count_conversion
likelihood_family
eps
likelihood_scale
```

Do not mix rate-valued `y_obs` with count-valued `lambda`, or the likelihood
temperature will become a hidden unit-conversion artifact.

### 4. Time Alignment Must Be Identical For All Observer Tables

The existing helper `_align_response_to_trace(response, n_timepoints)` returns
`response` when it has `T` frames and drops the first frame when it has `T+1`.
This alignment must be applied identically to:

- `y_obs`;
- `known_lambda_counts`;
- `zero_lambda_counts`;
- `prior_lambda_counts`.

Metadata should record:

```text
n_requested_timepoints
n_response_frames_before_alignment
n_timebins_after_alignment
alignment_rule
```

Otherwise known/zero/joint can silently compare different temporal bins.

### 5. Candidate Image Identity Can Be Too Easy

`random_global` may mostly measure trivial image separability. It is useful for
smoke tests but not for claims about trajectory marginalization.

Implementation should support the difficulty ladder from the start:

```text
self_lookup
random_global
same_session_region
matched_structure_bins
hard_negative_structure
matched_static_response
```

Every observed trial should record:

```text
candidate_ids
candidate_set_mode
n_candidates
nearest_distractor_contrast_distance
nearest_distractor_mean_rate_distance
nearest_distractor_static_response_distance
candidate_duplicate_flag
near_duplicate_flag
```

For Stage 2, the scientific readout should come from a matched/hard candidate
mode, with `random_global` only as a positive control.

### 6. Patch/Trajectory Coordinate Conventions Are Easy To Mix Up

The aggregate runner extracts a patch centered at the window mean gaze:

```text
center_px = gaze_deg_to_screen_px([mean_x_deg, mean_y_deg], ppd, screen_shape)
patch = _clip_patch(canvas, center_px, patch_size_px)
```

The traces generated by `_resample_trace` are mean-centered. Therefore the
trajectory passed into the twin is a relative retinal displacement around the
selected patch center.

Implementation guardrails:

- keep patch identity and trajectory identity separate;
- record patch center in screen pixels and source gaze degrees;
- record whether traces are mean-centered;
- use the same patch extraction path for true and distractor candidates;
- do not mix screen-centered static, trace-mean static, and patch-centered
  static baselines without explicit labels.

### 7. Leave-One-Out Must Exclude By Stable Trajectory Identity

LOO should not rely only on array position. Each trajectory needs a stable id:

```text
trajectory_id
family
scale
source_row
trace_bank_index
sample_index
raw_trace_hash or checksum
```

For non-leaky prior mode:

- exclude the exact observation trajectory id;
- optionally report nearest retained trajectory distance;
- detect duplicates or near-duplicates in the retained catalog.

If the exact trajectory is held out but a duplicate remains, LOO becomes
silently leaky.

### 8. Best-Single-Trajectory Score Must Stay Diagnostic

The best-single-trajectory diagnostic should use:

```text
best_score[i] = max_k log p(y_obs | I_i, tau_k)
```

over the same retained prior catalog used by joint-eye.

It should not be confused with known-eye or with a strict oracle upper bound on
accuracy:

- known-eye uses the true generating trajectory for every candidate image;
- best-single-tau uses the best retained prior trajectory for each candidate
  image;
- single-trajectory maximization can overfit distractor images, so marginalized
  joint accuracy can exceed best-single-tau accuracy.

If known-eye is high, best-single-tau is high, and joint is low, the issue is
evidence dilution. If known-eye is high but best-single-tau is low, the retained
prior catalog or likelihood model lacks support.

### 9. Likelihood Scale Can Masquerade As A Result

The Poisson score sums over many bins and units:

```text
n_timebins * n_units ~= 40 * 756
```

Even small rate mismatches can produce huge score differences. The
`likelihood_scale` should be treated as a sensitivity parameter:

```text
0.25, 0.5, 1.0, 2.0
```

Do not choose it by final test accuracy. Conclusions should state whether
joint-vs-zero and posterior localization are stable across the predefined grid.

### 10. GPU Throughput And Interference

`CanonicalTwinScorer.responses` can batch traces by concatenating rendered
stimuli. This is convenient but can spike GPU memory.

Safe defaults for first smoke runs:

```text
twin_trace_batch_size = 1
twin_batch_size = 16 or 24
n_timepoints = 40
n_candidates <= 8 or 16
n_prior_trajectories <= 4
```

Before larger runs:

- check `nvidia-smi`;
- use one GPU explicitly;
- use `nice`;
- write logs and pid files;
- avoid concurrent long runs on occupied GPUs.

## Proposed First Implementation Shape

### Package Modules

```text
declan/backimage_trajectory_observer/
  likelihood.py
  candidate_sets.py
  diagnostics.py
  observer.py
```

Keep response generation in the runner first, because it depends heavily on
BackImage project utilities.

### Runner Structure

```text
run_backimage_trajectory_table_observer.py
  parse args
  select windows
  build candidate sets
  build/generate observation and prior trajectory specs
  for each observed trial:
      load/extract candidate patches
      build y_obs response
      build known candidate responses under tau_true
      build zero candidate responses under static trace
      build prior candidate responses under retained tau catalog
      convert rates to counts
      write per-trial response table
      score known/zero/joint/best
      compute posterior diagnostics
      append observer row
  write summaries and report
```

### Minimal Cache Arrays

Per observed trial:

```text
prior_lambda_counts
known_lambda_counts
zero_lambda_counts
y_obs_counts
candidate_ids
prior_trajectory_ids
true_candidate_index
true_trajectory_id
nearest_prior_trajectory_id
zero_reference_mode
```

This is intentionally different from the earlier simpler schema that tried to
represent known and zero by indices into `lambda_counts`.

## Stage 0/1 Smoke Tests To Add Before Expensive Runs

1. Likelihood unit test:
   - exact matching candidate wins;
   - eps clipping avoids invalid logs;
   - likelihood scale preserves rankings when positive.

2. Observer unit test:
   - known, zero, joint, and best-oracle are distinct code paths;
   - LOO can score known-eye even when true trajectory is absent from prior;
   - posterior `N_eff` is finite and bounded by catalog size.

3. Candidate-set unit test:
   - true candidate appears exactly once;
   - duplicate candidate detection fires on repeated ids;
   - matched-structure mode returns requested candidate count or fails loudly.

4. Dry-run integration:
   - selected windows load;
   - candidate sets write;
   - trajectory metadata writes;
   - no twin inference required.

5. Tiny twin integration:
   - one or two observed trials;
   - `self_lookup` or easy `random_global`;
   - known-eye sanity passes;
   - cache shapes match metadata;
   - rerun with same seed gives identical CSV rows.

## Review Questions Before First Real Run

- Are observation trajectories and prior trajectories separated in metadata?
- Is known-eye computed under `tau_true` even in LOO mode?
- Is zero-eye computed under the declared primary zero convention?
- Are all rates converted to counts with one recorded `bin_seconds`?
- Is `eps` applied only to predictions, not observations?
- Does every posterior diagnostic refer to the same prior catalog as joint-eye?
- Are candidate sets hard enough to make the question nontrivial?
- Is the output chunked enough that Stage 2 will not fill memory or disk?
- Can a failed Stage 2 distinguish candidate difficulty, trajectory support,
  likelihood scaling, and posterior dilution?
